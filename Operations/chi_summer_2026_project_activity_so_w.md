## 1. Purpose

This Statement of Work defines the shared conceptual framework for Summer 2026 activity within the Center for Holistic Integration (CHI) in LG-038. The summer effort is not a single linear project. It is an integrated phase of overlapping CHI meta-project activity in which multiple student roles, technical systems, and creative research tracks are brought into productive relation.

The immediate purpose of the summer is to assemble core infrastructure, install and test selected systems, document the resulting architecture, and advance ongoing project development in ways that make future continuation practical. The goal is not to complete the full long-term vision of the Self-Aware Room, Blended Shadow Puppet, immersive audio environment, digital twin, or semantic mediation stack. The goal is to move these initiatives from partial specification and isolated experimentation toward a functioning, documented, extendable shared environment.

By the end of the summer, the project should yield a working room-scale system with enough operational continuity that future contributors can extend it rather than restart it.

## 2. Overall Framing

The summer work should be understood as a coordinated development phase across several overlapping CHI meta-projects. These include, but are not limited to, the **OAA Self-Aware Room**, the **AVMI immersive audio system**, **Blended Shadow Puppet Year 3/Act 3**, **Unity-based digital twin development**, **semantic mediation research**, which may include **quantum computing**, **AI/LLM integration**, and **CHI media/documentation** and **CHIIDS** infrastructure.

These initiatives are not subordinate components of a single master project. Each retains its own research and creative trajectory. The summer opportunity lies in their integration: shared room infrastructure, media systems, projection surfaces, audio playback, sensor pathways, documentation practices, and conceptual frameworks that allow contributions from different students to accumulate within a common environment.

LG-038 should therefore be treated as a persistent blended research environment rather than as a neutral classroom or temporary lab. The room is being developed as a configurable but continuous substrate for projection, spatial audio, distributed audio, triptych-based scenic/media structures, puppet performance, sensing, digital-twin representation, and future higher-level semantic or responsive behavior.

## 3. Summer Goals

The primary summer goals are as follows:

First, **assemble the basic physical and technical infrastructure needed to support ongoing room-scale work in LG-038**. This includes triptych-related structural development using TSlot 8020 modular framing hardware, projection surfaces using a variety of different projectors and projections surfaces, audio deployment and installation of an ATMOS 7.1.4 immersive sound system as well as peripheral distant field monitors, routing and integration with media servers for both visual and acoustical environments, the development of digital twin systems that integrate with these physical elements, and selected OAA-funded sensing and intelligant systems.

Second, **install and test at least a subset of the OAA-supported systems in a form that is operational rather than merely proposed**. This includes projection, immersive audio playback, selected distributed or localized audio strategies, triptych-related structures, and early sensing or technical-spine concepts where practical.

Third, **ensure that the core systems are documented clearly enough that future engineering, artistic, and research contributions can proceed on an informed basis**. The summer should produce records, diagrams, standards, repository structures, and process documentation rather than only physical build outcomes.

Fourth, **continue development of ongoing project activities in parallel**. Content, scripts, media, narrative systems, sound materials, music, worldbuilding, semantic frameworks, and virtual representations should continue to evolve alongside infrastructure work.

Fifth, **evaluate how flexible the room can be as an environment**. The summer should not only build fixed components, but also test how reconfigurable the space is with respect to multiple projection surfaces, triptych placement, immersive and distributed audio, performative use, and future sensing/computational extension, as well as integration with research, administrative, and exhibition areas.

Sixth, **establish the shared operational framework for the cohort**, including onboarding, communication, repository structure, and first-day orientation practices that allow the team to work as a coordinated summer unit rather than as isolated contributors.

Seventh, **generate meaningful product in multiples areas**, including academic and creative publications, performances, software, games, and integration into the shared fictive universe.

## 8. Control, Integration, and Software Mediation

The room will require both hardware integration and software integration. These should be treated as related but distinct design tasks.

At the software-control level, QLab is a plausible candidate for central distribution and show-level control because it provides a stable and well-understood environment for cueing media, audio playback, and event sequencing. If QLab is used in this central role, however, the project must determine carefully what it should and should not control.

A productive division of labor may be as follows:

QLab may function best as the high-level cue, playback, and operator-facing control environment. In this role, it can manage media playback, cue ordering, timeline logic, manual triggering, and selected outbound messages to other systems.

TouchDesigner may function best as a real-time mediation, transformation, visualization, and state-processing environment. In this role, it can receive live data, process sensor or interaction streams, manage dynamic visual behavior, perform mappings or parameter transformations, and return status or trigger information to other systems.

Under this model, QLab acts as the stable show-control and playback layer, while TouchDesigner acts as the real-time adaptive layer.

This relationship is likely to be productive when communication is explicit and bounded. Practical interfacing methods may include OSC, MIDI, network messaging, file/state handoff, or other clearly documented API-level exchanges.

Potential productive interactions include:

- QLab sending cue-state or transport triggers to TouchDesigner;
- TouchDesigner returning processed state information, completion signals, or trigger recommendations;
- QLab initiating reliable playback events while TouchDesigner handles reactive visuals or sensor-linked transformations;
- TouchDesigner aggregating live room or interaction data into forms that QLab can use as bounded control inputs.

Potential conflicts should also be anticipated.

The most likely conflict is authority ambiguity: if both systems are allowed to act as primary controllers, contradictory logic may emerge. QLab generally assumes a cue-based, operator-centered model, whereas TouchDesigner can encourage continuous, event-driven, or generative behavior. If both are used without a clear hierarchy, the system may become difficult to debug, difficult to reproduce, or unstable in performance.

A second likely conflict is temporal mismatch. QLab is strongest when events are discrete, intentional, and stage-manager legible. TouchDesigner is strongest when behavior is continuous, reactive, and computationally fluid. The project should therefore avoid forcing either system to behave like the other.

A third conflict concerns debugging and documentation. As more pathways are added between cue logic, sensor logic, dynamic parameter mapping, and media output, the room can become difficult to maintain unless API boundaries and message vocabularies are documented explicitly.

For this reason, a likely best-practice direction is:

- use QLab as the primary operator-facing cue and distribution environment;
- use TouchDesigner as a subordinate or parallel real-time mediation layer;
- define a limited and explicit API between them;
- keep authority, override, and fail-safe behavior legible;
- document all message pathways, naming conventions, and expected states.

This question should remain open to refinement through summer testing rather than being declared solved in advance.

## 10. Working Principles

The summer project should be guided by the following principles.

### 7.1 Infrastructure First, but Not Infrastructure Only

The summer must produce real infrastructure. However, infrastructure should always remain tied to content, performance, research, and creative use rather than becoming an end in itself.

### 7.2 Modularity and Extendability

Systems should be designed and documented so that later contributors can add, replace, or reinterpret components without undoing all prior work.

### 7.3 Overlapping Meta-Projects, Not Forced Unification

Projects should not be artificially collapsed into a single storyline. Their productive overlap should be clarified through interfaces, not through false uniformity.

### 7.4 Documentation as Construction

Documentation is not an afterthought. In this context, diagrams, naming conventions, repository structures, calibration notes, media records, and testing logs are part of the system itself.

### 7.5 Conceptual Clarity Before Overclaiming

This version of the SoW is intentionally conceptual and design-oriented. It should establish sound structure, language, and priorities without pretending that all engineering questions are already resolved.
