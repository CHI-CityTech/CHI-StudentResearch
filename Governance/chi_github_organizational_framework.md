# CHI GitHub Organizational Framework
## Summer 2026 Active Structure, Lifecycle Logic, and Repository Roles

## 1. Structural Premise

The CHI GitHub organization should function simultaneously as:

- a resource center for CHI meta-projects;
- a production-management hub for active work;
- a durable home for student and project documentation;
- a lifecycle system in which active, quiescent, archived, and emerging projects remain legible.

This framework builds on the existing CHI GitHub ecosystem rather than replacing it. CHI already uses GitHub as a meta-project system in which long-horizon hubs support active subprojects, student work, curricular activity, infrastructure, and public-facing materials. The goal of this framework is therefore not to start over, but to clarify how Summer 2026 work should be organized within that structure.

## 2. Core Organizational Logic

The CHI GitHub system should be understood as layered.

### 2.1 Meta-Project Repositories

Meta-project repositories serve as persistent, long-horizon conceptual and organizational hubs. These repositories should remain relatively stable and function as entry points, resource centers, and continuity structures.

Examples include the existing META repositories and other structurally equivalent top-level CHI repositories.

These hubs should:

- define the meta-project’s scope and identity;
- link to associated active subprojects;
- preserve continuity across semesters and cohorts;
- provide orientation, key resources, and historical trace.

### 2.2 Active Project / Subproject Repositories

When work within a meta-project becomes technically, creatively, or operationally complex, it should move into a dedicated active project or subproject repository.

These repositories are the primary homes for ongoing development, working files, technical documentation, coordination artifacts, and deliverables.

They should be used when a line of activity has enough density that it should not live only as a folder, branch, or appendix inside the meta-project repository.

### 2.3 Student Research and Participation Layer

The CHI-StudentResearch repository should continue to function as the student-management and participation layer. Its role is not to absorb all final project artifacts, but to support student proposals, participation tracking, research management, and related coordination across meta-projects.

Student work should remain connected to CHI-StudentResearch administratively while actual production materials live in the appropriate active repository.

### 2.4 Curricular and Course Repositories

Course and curriculum repositories should remain legible as a distinct layer. These may connect to one or more meta-projects, but they serve academic delivery, instructional design, reusable teaching structures, and course-based participation.

### 2.5 Archive and Quiescent Status

Not all repositories need to remain actively developed at all times. Some should enter a quiescent or archived status while remaining accessible as part of the CHI ecosystem.

Archived repositories are still useful because they preserve documentation, code, media, and historical continuity. They should remain discoverable but clearly identified as not currently active.

Deletion should be reserved for redundant, accidental, empty, or otherwise non-valuable repositories.

## 3. Role of META-CHIIDS

META-CHIIDS should serve as the governance and systems-logic repository for the GitHub ecosystem itself.

This makes it the appropriate place to define:

- classification rules for repository types;
- lifecycle states such as active, quiescent, archive, or deprecated;
- naming conventions where useful;
- topic/tag standards;
- relationships among meta-project hubs, student activity, and production repositories;
- guidance on documentation, discoverability, and repository stewardship.

META-CHIIDS should not necessarily hold all project files directly, but it should define how the overall system is organized and how work becomes legible across the ecosystem.

## 4. Summer 2026 Organizational Need

The immediate challenge for Summer 2026 is not to redesign the whole CHI GitHub organization at once. The immediate goal is to identify and support the specific set of repositories needed to make Summer 2026 activity function effectively.

This means identifying:

- which repositories are active for Summer 2026;
- which repositories are continuing from earlier phases and must remain active;
- which repositories should support room-centered infrastructure;
- which repositories should support specific production workstreams;
- which repositories may move toward archive or quiescent status later.

## 5. Recommended Summer 2026 Active Repository Set

### 5.1 META-CHIIDS

Role: governance, classification, documentation infrastructure, and CHI-wide systems logic.

Summer relevance:
- define the classification and lifecycle framework;
- support documentation logic across active summer repositories;
- clarify how active, student, curricular, and archived repositories should relate.

### 5.2 CHI Summer 2026 Operations (new)

Role: central operations and production-management hub for the Summer 2026 cohort.

This repository should hold:
- launch and initial task documents;
- shared room systems charts;
- cabinet, shelving, and workspace-allocation plans;
- first-day and initial task lists;
- inventory normalization work;
- cross-workstream task tracking;
- B&G/IT/architectural coordination drafts;
- links outward to the actual working repositories.

This repository should not replace the project-specific repositories. It should function as the central coordination surface.

### 5.3 OAA Self-Aware Room (new)

Role: room-centered infrastructure and integration repository.

This repository should be the primary home for:
- room-level architecture and systems integration;
- OAA-funded infrastructure documentation;
- triptych system development and associated structure logic;
- projection infrastructure and surface planning;
- immersive and distributed audio integration at the room level;
- sensor/system layout as it pertains to the room;
- cabinet, rack, storage, and workspace plans where these affect the room system;
- facilities-facing and infrastructure-facing documentation related to the room.

This repository should not be reduced to audio-only content. It is the room integration repository.

### 5.4 AVMI-GVSC-SoundSystem (existing)

Role: specialized immersive-audio lineage and partner-context repository.

This repository should remain the home for:
- AVMI/GVSC sound-system modeling and simulation context;
- partner-facing immersive-audio continuity;
- specialized technical logic tied to the AVMI project;
- higher-level sound-system research lineage.

Relationship to the OAA room repository:
The OAA room repository is the room-centered integration environment. AVMI-GVSC-SoundSystem remains the specialized audio-system and simulation repository. The immersive-audio subsystem links them.

### 5.5 META-Blended-Shadow-Puppet and Blended-Shadow-Puppet-Theatre (existing)

Role: BSP hub and active theatrical/production development.

These repositories should remain central for:
- Year 3 / Act 3 BSP production development;
- performative, material, narrative, and theatrical work;
- triptych use as a performative object;
- UNESCO-facing BSP continuity where relevant.

### 5.6 Unity-BSP (existing)

Role: digital twin and virtual-physical mapping repository.

This repository should remain active for:
- mapped virtual twin work;
- LG-038 and BSPT stage logic;
- updates to the taller/extended-height triptych system;
- related Unity-side documentation and standards.

### 5.7 Documentary (existing)

Role: documentary, archival, interpretive, and promotional media repository.

This repository should remain active for:
- CHI-aligned video documentation;
- BSP and room-development documentary materials;
- artistic/promotional short-form media;
- media workflows that support archive and dissemination.

### 5.8 Continuing Student or Specialized Repositories

Some student and project repositories already exist and should remain active where they are still in use. Summer 2026 should not force all such work into new seasonal repositories if the work already has a meaningful home.

Examples may include:
- Blended_Music;
- Personalized-LLM;
- other project-specific repositories whose work is continuing and active.

## 6. Personalized LLM and the Self-Aware Room

Personalized-LLM should be treated as relevant to the Self-Aware Room ecosystem rather than as an unrelated AI-only initiative.

The room architecture is expected to involve multiple forms of AI, middleware, and layered processing across different stages of sensing, abstraction, semantic interpretation, response, and mediated behavior. Personalized LLM work may therefore contribute to the room not as a single monolithic intelligence, but as one or more specialized AI agents or middleware elements within the broader room design.

This means:

- Personalized-LLM should remain visible as part of the Collaborative AI ecosystem;
- its practical relationship to the Self-Aware Room should be documented clearly;
- the OAA Self-Aware Room repository should cross-link to Personalized-LLM where AI agents or middleware are relevant to room operation;
- room design should account for multiple computational layers rather than assuming one central AI system.

In this sense, Personalized-LLM is part of the room’s evolving technical and conceptual ecosystem, especially where distinct AI roles may mediate different parts of sensing, control, semantic interpretation, or interaction.

## 7. Recommended Classification Approach

Repository names should remain readable and reasonably self-descriptive, but names alone should not carry the full classification burden.

A hybrid system is recommended:

- repository names provide basic structural identity;
- topics/tags provide lifecycle state, domain, and cross-cutting classification;
- README files explain role and relationships.

This avoids overloading names while still making repositories legible.

## 10. Summary

The CHI GitHub ecosystem already contains the foundations of a strong meta-project-based structure. Summer 2026 does not require a total redesign. It requires a clearer operational layer, a room-centered integration repository, a central summer operations repository, and an explicit governance framework for active, continuing, and archived work.

META-CHIIDS should hold the logic of this framework. The new OAA Self-Aware Room repository should hold room-centered integration work. AVMI-GVSC-SoundSystem should remain the specialized immersive-audio lineage repository. Personalized-LLM and related AI systems should be understood as part of the room’s broader middleware and AI ecosystem where relevant.

The immediate task is to activate the right repositories for Summer 2026 while building a classification framework that can later support cleanup, archiving, and long-term CHI continuity.
