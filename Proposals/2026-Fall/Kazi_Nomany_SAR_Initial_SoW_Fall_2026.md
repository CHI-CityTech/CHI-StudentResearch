# Initial Statement of Work
## SAR Repository Review, Documentation, and Student Research Infrastructure

**Student:** Kazi Nomany  
**Position:** Federal Work-Study — CHI Technical Documentation and Systems Reporting Assistant  
**Project:** SAR  
**Term:** Fall 2026  
**Supervisor:** Dr. David B. Smith  
**Center:** Center for Holistic Integration (CHI), New York City College of Technology, CUNY

### 1. Purpose

This initial assignment will introduce the student to the SAR project, its existing documentation, and the GitHub-based workflow used by CHI for collaborative technical and research development.

The work has two immediate purposes:

1. Improve the accuracy, organization, and usability of the existing SAR GitHub repository.
2. Establish a Fall 2026 student-research structure that can be reviewed and developed collaboratively as additional researchers and projects are confirmed.

This assignment also establishes the version-control workflow that will normally be used for subsequent SAR and CHI development work.

### 2. Repository Setup and Working Method

The student will begin by cloning the SAR GitHub repository to a local computer.

Rather than making changes directly to the main branch, the student will:

- create a dedicated working branch;
- perform all assigned edits and additions within that branch;
- commit work regularly using clear and descriptive commit messages;
- push the branch to GitHub; and
- review the proposed changes with the supervisor before anything is merged into the main branch.

This **clone → branch → edit → commit → push → review → merge** process will serve as the general workflow for future repository-based assignments unless otherwise specified.

The purpose of the branch is not merely to protect the main repository. It creates a reviewable record of proposed changes and provides an opportunity to discuss documentation, organization, and technical decisions before they become part of the project.

### 3. SAR Repository Audit

Review the current SAR GitHub repository systematically.

Begin with the main README and follow the documentation and resources referenced there, including the documentation identified near the bottom of the README.

The review should examine:

- whether links function correctly;
- whether links point to the intended resource;
- whether referenced files and directories actually exist;
- whether descriptions accurately represent the current project;
- whether information has become obsolete;
- whether repository navigation is understandable;
- whether naming and organizational conventions are consistent;
- whether documentation duplicates or contradicts information elsewhere in the repository; and
- whether important information appears to be missing.

Do not silently correct uncertain information. If something appears inaccurate but the correct information cannot be established from the existing project materials, identify it for discussion.

### 4. README Review and Update

Based on the repository audit, prepare updates to the SAR README.

Correct straightforward problems such as broken links, incorrect paths, outdated references, typographical errors, and clearly obsolete information.

Where more substantial changes appear necessary, identify the problem and propose a correction rather than assuming what the project documentation should say.

The README should ultimately provide a reliable entry point for someone encountering SAR for the first time and should accurately direct researchers to the project's principal documentation and resources.

### 5. Fall 2026 SAR Scope

Review the existing SAR documentation to develop an initial understanding of the project's current state and its Fall 2026 scope.

The immediate goal is orientation rather than rewriting the project definition. Note:

- what appears to be currently active;
- what appears to be planned;
- what appears to have been completed;
- what remains unclear;
- where documentation does not reflect the current state of the project; and
- questions that need to be resolved with the project supervisor or other researchers.

These observations should inform both the README review and subsequent organization of Fall 2026 student research.

### 6. Fall 2026 Student Research Directory

Within the repository's **Student Research** area, create an appropriate **Fall 2026** directory under **Proposals**, following the organizational conventions already established in the repository where applicable.

This directory will become the working location for Fall 2026 SAR student research proposals.

Begin constructing the directory from the information currently available, but do not assume that the existing researcher list, project assignments, titles, or descriptions are necessarily correct.

Identify:

- researchers who are clearly confirmed;
- projects or assignments that are clearly documented;
- information that appears outdated or incorrect;
- duplicate or inconsistent entries;
- researchers or projects whose status is uncertain; and
- information that needs confirmation.

The student and supervisor will review this material together before the Fall 2026 research structure is considered authoritative.

### 7. Issues and Questions Log

As part of the repository review, maintain a concise record of issues discovered.

For each significant issue, record:

- location in the repository;
- nature of the problem;
- whether the issue was corrected;
- proposed correction if one is apparent; and
- questions or decisions requiring supervisor review.

This log can be maintained as an appropriate Markdown document, GitHub issue structure, or other repository-based mechanism determined during the assignment.

### 8. CHI Web Interface Exploration

As a secondary exploratory task, examine **Dribbble** and comparable examples of contemporary research, design, technology, and interdisciplinary project websites.

The purpose is not to redesign the CHI website immediately. Instead, consider how CHI might eventually develop a more professional, visually coherent, and interactive public-facing interface capable of representing:

- CHI and its overall research identity;
- individual meta-projects such as SAR;
- researchers and collaborators;
- student research;
- project documentation;
- relationships among projects; and
- public-facing research outcomes.

Collect a small number of useful examples and briefly identify what each example suggests for CHI in terms of information architecture, navigation, interaction, visual presentation, or project discovery.

### 9. Initial Deliverables

The initial assignment should result in:

- a locally cloned and functioning SAR repository;
- a dedicated Fall 2026 working branch;
- an audit of the existing repository and README;
- corrected broken or inaccurate links where the correction is unambiguous;
- proposed README updates;
- a Fall 2026 directory within the Student Research/Proposals structure;
- an initial review of Fall 2026 researchers and research projects;
- a record of errors, uncertainties, missing information, and questions requiring review;
- the completed branch pushed to GitHub for supervisor review; and
- a short collection of web-interface references and observations relevant to future CHI public-facing development.

### 10. Review and Completion

The assignment is not complete when the branch is pushed.

The student and supervisor will review the branch together, examine the proposed changes, resolve questions identified during the audit, and make any necessary revisions.

Once the work has been reviewed and approved, the branch can be merged into the appropriate main project branch.

This review-and-merge process will establish the normal working pattern for subsequent SAR assignments.
